## Candidates

### C1 — Scroll-state container queries (`container-type: scroll-state`) *(shipped 2026-06-14)*

CSS-only detection of `stuck` / `snapped` / `scrollable` states (Chrome 133+). `@container scroll-state(stuck: top) { … }` adds a shadow when a sticky bar is actually stuck. Pure progressive enhancement — non-supporting engines keep today's static treatment, no JS fallback needed. Compositor-friendly, on-doctrine.

**Containment caution resolved:** the original caution worried `container-type` creates containment that could interact with the panel-compositor rules ([panel-compositor-load.md](panel-compositor-load.md)). Verified against MDN/web.dev: **`container-type: scroll-state` applies NO containment** — unlike `size`/`inline-size`, it creates no new containing block, stacking context, or layer promotion. So it is free to use even inside the detail panel. (The two-value form `size scroll-state` *would* add size containment; we use the bare `scroll-state` value, which doesn't.)

**Spec-vs-reality on the named targets:** § C1 originally named `champion-sticky-strip`, editorial chapter chrome, and the scroll-to-top button. Two don't fit the `stuck:` mechanism and were deliberately excluded (not silently dropped):
- **scroll-to-top button** — [`position: fixed`](../../../apps/web/src/components/scroll-to-top.tsx); `stuck` only applies to `position: sticky` elements, so it has no stuck state. Its show/hide stays JS-gated (500px threshold + panel-open suppression, which CSS can't replicate).
- **editorial chapter chrome** — the genuinely-sticky surface is the full-viewport pinned [`data-chapter-stage`](../../../apps/web/src/home/recap/chapter-multi-beat.tsx) / [`data-chapter-pin`](../../../apps/web/src/home/recap/chapter-container.tsx). A drop shadow on a full-bleed editorial spread has no natural affordance and the surface is design-spec-governed ([subject-chapter-design-spec.md](subject-chapter-design-spec.md)), so it was left static. Owner-confirmed surface set: panel chrome + page nav.

**Shipped shape:** a shared mechanism in [motion.css](../../../apps/web/src/styles/motion.css) § scroll-state — `[data-stuck-container] { container-type: scroll-state }`, and `@container scroll-state(stuck: top) { [data-stuck-shadow] { box-shadow } }` (the query styles *descendants* of the container, never the container itself, so each surface carries a transparent `pointer-events-none absolute inset-0` shadow-carrier child). Applied to (1) the panel sticky chrome wrapper `<div className="sticky top-0 z-40">` in [slide-panel.tsx](../../../apps/web/src/_shared/slide-panel.tsx) — the real "champion-sticky-strip" surface (the strip renders inside this wrapper), and (2) the page [nav](../../../apps/web/src/components/nav.tsx) (already carries `inset-x-0 bottom-0` hairline decorations, so the carrier matches its idiom). The `@container` line needs a `biome-ignore format:` — Biome 1.9 doesn't know the `scroll-state()` functional notation and inserts a space that reparses it as a container-name + size query, silently breaking the match. No paint-budget regression expected: the shadow only paints when a bar is *stuck* (after scrolling), never at cold load / panel-open (both measured at scrollTop 0), and `container-type: scroll-state` promotes no layer.

### C2 — CSS Custom Highlight API for palette match-highlighting *(shipped 2026-06-13)*

`CSS.highlights` + `::highlight()` (Baseline 2023 — inside floor) to highlight matched substrings in ⌘K palette results without wrapping `<span>`s. Zero DOM churn during type-ahead — the perf-meets-polish detail the palette deserves.

**Shipped shape:** [lib/highlight-matches.ts](../../../apps/web/src/lib/highlight-matches.ts) owns the API surface — `supportsHighlightApi()` (feature-detect), `paintMatchHighlights(root, needle)` (rebuilds `Range`s over every case-insensitive hit inside `[cmdk-item]` rows under `root`, registered as the named `"palette-match"` highlight), and `clearMatchHighlights()`. [command-palette-dialog.tsx](../../../apps/web/src/components/command-palette-dialog.tsx) drives it from a `useEffect` keyed on `[open, parsed.freeText]`: the needle is the free-text residual (so structured verbs like `win` / `with:Jax` never paint stray hits), and a `MutationObserver` on the list element catches async row arrival (infinite-loaded matches, champion/Steam data) while the needle is stable. Scoped to `[cmdk-item]` so group headings and the empty-state never tint. The `::highlight(palette-match)` rule lives in [index.css](../../../apps/web/src/index.css) next to `::selection`, theme-tinted via `color-mix(... var(--theme-fg) ...)`. Tested in [highlight-matches.test.ts](../../../apps/web/src/lib/highlight-matches.test.ts): happy-dom lacks the API so `supportsHighlightApi()` is `false` and `paintMatchHighlights` is a verified no-op; the range-recompute / clear-on-empty / clear-on-no-match / heading-exclusion paths run against a stubbed registry.

### C3 — `text-box-trim` on editorial type *(shipped 2026-06-13)*

Cap-height/alphabetic trimming (Baseline 2025 — inside floor) for `SectionTitle` / `CardTitle` / recap display numerals. Kills the invisible half-leading that makes optical alignment with chips and borders approximate today.

**Shipped shape:** one Tailwind v4 `@utility trim-cap { text-box-trim: trim-both; text-box-edge: cap alphabetic; }` in [index.css](../../../apps/web/src/index.css), applied at the primitive level in [section-title.tsx](../../../apps/web/src/components/ui/section-title.tsx), [card-title.tsx](../../../apps/web/src/components/ui/card-title.tsx), and [hero-number.tsx](../../../apps/web/src/components/ui/hero-number.tsx) (the single-change-point principle from the header-primitive migration — `HeroNumber` propagates to every recap numeral via `HeroPair`). Verified in a `vite preview` build via Playwright (Chromium 148): computed `text-box-trim: trim-both` / `text-box-edge: cap alphabetic` resolve and the `SectionTitle` layout box drops 18 px → 10 px, pulling headers optically flush. Pure progressive enhancement — Firefox (no `text-box-*` support today) silently keeps the prior spacing, no fallback needed.

**Gotcha that cost a build cycle — do not name a custom Tailwind utility `text-*`.** The utility was first named `text-trim-cap`; `cn()` (tailwind-merge) classifies any `text-…` token as the colour/size group and silently dropped it when it sat beside `text-foreground` / `text-sm` in the same `className`. The class was present in the built JS but absent from the rendered DOM (computed `text-box-trim: none`). Renaming to `trim-cap` fixed it. Any future custom utility that must coexist with `text-*` classes in a merged className needs a non-`text-` name (or a tailwind-merge config extension).

### C4 — `mask-image` for edge fades + editorial reveals

Two applications, originally ordered C4.1 then C4.2:

1. ~~**Gradient masks on scroll-overflow edges** (screenshot strip, sticky strips) replacing overlay-div fades — fewer stacked elements, real transparency over the backdrop.~~ **C4.1 closed 2026-06-14 — no work to do.** An audit of every scroll strip in `apps/web/src` found the premise already satisfied or inapplicable: the only true scroll-edge fades (trophy-case-strip, nav splash) already use `mask-image`; the screenshot strip uses Embla's `Fade` plugin (slide crossfade, no edge to fade). The remaining bare `overflow-x-auto` strips are **not** decorative hard-cuts but data surfaces where an edge mask would hide real content: match-build-order is `flex-wrap` (no horizontal scroll), match-skill-order is a level grid (masking the right edge hides the last skill column), match-event-timelines only scrolls when zoomed and a mask would clip boundary kill events, and the slide-panel tab header uses a label-hiding strategy that prevents overflow. A static both-edge fade also clips the first item at rest unless gated on `scroll-state(scrollable:…)`, which Firefox/Safari don't support. **Do not re-suggest C4.1** — there is no low-risk, positive-value target.
2. **Scroll-driven mask wipes on chapter imagery** — `animation-timeline: view()` driving `mask-position`/`mask-size` so a splash "develops" on scroll. Fits the recap's editorial language better than opacity fades, and avoids the [[ancestor-opacity-suppresses-backdrop-filter]] trap by not touching `opacity` at all. **C4.2 still open** — rides the next recap-chapter touch so the paint-probe cost is shared.

Mask layers can affect compositing — probe before/after per the paint-budget workflow on any route in the budget table.

### C6 — `offset-path` on the match map overlay *(shipped 2026-06-14)*

[match-map-overlay.tsx](../../../apps/web/src/lol/matches/match-map-overlay.tsx) already has kill/death coordinates. Animate a marker along a death-walk / roam path with CSS motion path (`offset-path: path(…)` built from the coordinate series). Pure CSS, compositor-friendly, and a data-viz flourish no LoL dashboard has — strong case-study material. Reduced-motion variant: static dotted path, no marker travel.

**Shipped shape:** a `myPath` memo in [match-map-overlay.tsx](../../../apps/web/src/lol/matches/match-map-overlay.tsx) traces the player's **actual movement** — their sampled `position` at each timeline frame (`timeline.data.frames[].perParticipant[myParticipantId].position`, ~once a minute), applying the same `15000 - y` flip as `MapDot` so the path lands on the dots' user space. Frame 0 is spawn, so the path begins in the player's base organically (no synthetic fountain) and follows where they really went. *(An earlier draft connected kill locations instead — rejected because straight lines between fights imply teleporting between kills; the per-frame positions are the real route and were already plumbed through the shared `MatchTimelineFrame` type.)* `roamPathD` builds an `M…L…` polyline (null below 2 frame positions). Rendered in a `<g>` *before* `visibleEvents.map` so the dots sit on top: a static dotted `<path>` (`strokeDasharray="1 440"` round-cap dots, the full reduced-motion experience) plus, when `!reduced`, a `.map-roam-comet` `<circle cx=0 cy=0>` whose `offset-path` is set inline (`path("${roamPathD}")`, data-driven) and whose travel lives in [motion.css](../../../apps/web/src/styles/motion.css) § roam-path comet (`offset-distance: 0%→100%` keyframe, duration wired via a `--roam-duration` var derived from point count). The comet is **user-initiated** — a "Trace my route" button on the map panel bumps a `playCount`, and the `<circle>` is keyed on it so each click restarts the travel from spawn (no autostart, which earlier read as "already playing" the instant the map opened). It plays **once per click** at **constant speed** (`linear` — offset-distance is arc-length-measured, so an eased curve lurches fast-through-the-middle; `animation-fill: forwards` holds at the final position), never an infinite loop. The static dotted `<path>` is always visible so the route reads even before the user traces it. Duration scales with frame count (`min(16, max(7, frames × 0.6))s`) — a deliberate, watchable pace rather than a quick flash. Decoupled from the dot filters / time-window brush so it reads as a stable whole-game layer, not a flickering one.

Three load-bearing details: (1) **offset-path on an SVG element resolves path() in the element's user space** (the `0 0 15000 15000` viewBox) — so coordinates align with the dots for free, no screen-px conversion despite the letterboxed (`xMidYMid meet`) map. (2) **`cx`/`cy` are 0** so the circle's centre rides the path point (the element's own position otherwise *adds* to the offset). (3) **No SVG `transform` attribute on the comet** — it conflicts with offset-path on Firefox ([bug 1565147](https://bugzilla.mozilla.org/show_bug.cgi?id=1565147)). Progressive enhancement: `@supports (offset-distance: 0px)` gates the comet's opacity/animation, so engines without motion-path keep the comet invisible and the static dotted path is the whole experience (and `@media (prefers-reduced-motion: reduce)` hides it as a CSS backstop on top of the JSX gate). **No paint-budget probe applicable** — the map overlay is an on-demand modal opened from match-detail, not one of the baselined route scenarios; it adds nothing at any route's cold load, and the only interactive cost is one path + one offset-distance-animated circle (a translate, compositor-only) inside an already-open dialog. Tests in [match-map-overlay.test.tsx](../../../apps/web/src/lol/matches/match-map-overlay.test.tsx): path present at ≥2 owner fights, absent below 2, comet data-driven when motion allowed.
