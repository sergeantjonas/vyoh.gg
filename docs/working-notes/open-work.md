### Pre-deploy / admin

- **Route-loader failure policy — settled 2026-08-08.** The original finding (2026-08-02, while landing the Steam Portrait) was that `/steam` returned **HTTP 500 with no page at all** when its loader awaited an endpoint the running api did not have. Re-measured before acting, and half of it had already been fixed by something else: chunk 5's router-level `defaultErrorComponent` landed *after* that measurement, so a rejected loader now keeps the shell and fails one region, and a broken endpoint no longer splashes across routes — with only `/steam/wishlist` failing, `/`, `/steam` and `/steam/achievements` all served 200 with full content. What survived was narrower and worth fixing on its own terms: **the failing route answers HTTP 500 on a document that renders correctly**, which for an indexable route converts an upstream blip into a de-indexing. Blanket `.catch()` was the wrong shape, and so was blanket priming. The rule that landed: **swallow the prime when the primed query is one region of a page that still says something true without it; let it reject when the primed query is the page**, because a 200 over an empty state teaches a crawler the page is empty while a 500 asks it to come back. Tolerated via `primeQuietly` — `/lol/$accountSlug` (rank + live, two chips on a page carrying the champion pool and season history), `/lol/patches/$version`'s patch **list** (supplies only the release date), `/steam/portrait` (adopted the helper, behaviour unchanged). Deliberately fatal, each with the reason recorded at the loader — `__root.tsx` (no identity, no app), `/lol/patches` (the list picks the version), `/lol/patches/$version`'s **changeset**, `/steam/wishlist`, `/steam/achievements`, `/lol/$accountSlug/matches`. Verified end-to-end against a proxy that fails one endpoint while the api stays up: `/lol/ahri` went 500 → **200 with 25 kB of real page** while the unguarded `/lol/ahri/matches` stayed 500 under the same failure, and `/lol/patches/26.3` served **143 kB of patch notes** with its list endpoint down. Pinned by `apps/web/src/route-loaders.test.ts`. → [tanstack-start-migration.md](cross-cutting/tanstack-start-migration.md)
- **`PatchesPage` held its skeleton forever on a failed patch list — fixed 2026-08-08.** Its loading gate read `!patchChanges && (patchList === undefined || changesPending)`, using `data === undefined` as a proxy for "still loading". A query that *errors* leaves `data` undefined too, so an outage parked the page on its skeleton with nothing left to advance it. The route loader hid this on a cold load — a failed prime rejects into the route-tier error card before the component mounts — leaving it reachable only on the paths the loader does not cover: a background refetch that fails, or a client-side navigation after the cache expired. Now bails to a `PatchesUnavailable` with a retry, kept deliberately distinct from `PatchesEmpty` because "no patches synced yet" is a claim about the sync schedule and sends a visitor away to wait for something that already happened. The bail is narrower than "either query failed", so it does not undo the `$version` loader's tolerance of a failed list: with the version in the path there is still a full page to render, and only the release date is lost. **`MatchList` was wrongly named alongside it** — the query lives in the route layout, which already carries an error message plus a retry button; the component only receives an array. `/lol/$accountSlug/matches` stays fatal because the list is the route, not because it cannot degrade.

- **Ingestion cron reliability** — **three self-sealing gates fixed 2026-08-05**, opened by a real symptom: nine Steam achievements earned in 24 h were not ingested at all. The defect class is *a cached upstream fact that gates downstream work and is only re-derived by a rare cron*. Here a game bought pre-release recorded `achievementCount = 0`, all four unlock paths gate on `> 0`, and the boot backfill skips rows that exist — so the more it was played, the more often the hourly poller saw it and no-opped. `@nestjs/schedule` does not replay a missed fire, and three measurements showed the long-interval crons have effectively never run on the dev box: the weekly schema cron has **no** 05:00 timestamp in the table (both recorded runs were boot backfills), the 2026-08-02 rarity cron didn't fire, and the tag catalog's newest row is 2026-07-15 against a monthly cron. Fixed: recently-played re-checks empty schemas before its unlock loop, the tag poller's boot check reads catalog *age* not row count, `refreshSchemas` guards its write per appid (one failure used to abort every appid behind it), and `refreshUnlocksForGame` asserts `count > 0` rather than `!== 0` on a nullable column. **Arc complete 2026-08-06:** all four long-interval pollers now select on age rather than on a wall-clock fire — schema and rarity daily against a 7-day window, enrichment daily against 30 days OR'd with its existing `logoPath IS NULL` predicate, tag catalog on boot. The boot pass is the load-bearing half, since a daily cron at 05:00 on a machine that is off at 05:00 still never fires; the daily tick carries it once hosting makes the process continuous. Each was verified against the live database rather than mocks — rarity's first run found the backlog the never-fired Sunday crons had left and drained it 40 per pass instead of one 158-call burst. Residual risk is a day rather than a week or a month. Three notes kept in the doc: the batch cap must stay above the steady-state arrival rate or the oldest rows never drain, `orderBy` needs `nulls: "first"` because Postgres sorts NULLS LAST on ASC (which would reintroduce this same starvation one layer down), and the three selections were deliberately *not* extracted into a shared helper — they share a concept, not a shape. → [ingestion-cron-reliability.md](ops/ingestion-cron-reliability.md)

- ~~**Pin `timeZone` in the date formatters**~~ — **SHIPPED 2026-08-07.** The deploy sets `TZ=Europe/Brussels` on the containers, which makes the server agree with a browser *in that zone*. It does not fix a visitor elsewhere: ~25 `Intl.DateTimeFormat`/`toLocaleDateString` sites across `apps/web/src` resolve to the ambient zone, so for anyone outside Brussels the server and client still disagree on any date near midnight and React discards the server tree. Three sites already pin it (`ambient-hero`, `wishlist/upcoming/bucketing`, `profile-lp-history-constants`), so the pattern exists; this is a sweep, not a design. **Landed in four commits 2026-08-07.** `OWNER_TIME_ZONE` in `@vyoh/shared` replaced the twenty-odd copies of the literal and its six local `TIME_ZONE` constants; every date formatter in `apps/web/src` now names a zone.
