# Steam — per-game "fetch now"

**Status:** Shipped — both chunks landed 2026-09-05: the owner-only route and the refresh control on the game page.

Read this when: touching `POST /steam/game/:appid/refresh`, `SteamGameRefreshService`, or adding another owner-only trigger that reports its result in the response rather than on the status board.

Wished 2026-09-05 after the Steam-private finding in [ingestion-cron-reliability.md](../ops/ingestion-cron-reliability.md): two games sat unstamped for days and the only way to see whether a fix had landed was to wait for the next four-hourly sweep.

## Why

Every Steam poller runs on a cadence chosen for the whole library — four-hourly unlocks, daily schema and rarity against a seven-day window, daily enrichment against thirty. That is right for 160 games and wrong for the one game the owner just finished a session in, or just marked private, or just bought. The status page can force a whole-stream run, which spends the Steam budget on 159 games to answer a question about one. A per-game control pulls only that game's five legs and says what changed, so the owner can verify a fix or refresh a stale panel without waiting for a cron or burning the sweep.

## Decisions

- **The response carries the result; the registry carries the guard.** Status-page triggers go through `SyncJobRegistry.trigger()`, which returns before the work finishes because a patch sync takes minutes. A per-game refresh is five Steam calls and a few seconds, and the point of clicking is to read what changed, so the route awaits the work. It still runs through the registry — `execute()` is `run()` with the result returned and the failure rethrown — so the overlap guard, the duration and the last outcome land on the status board like every other job. `steam-game-refresh` is the first catalog entry with `cron: null`; the board renders "on demand" in its place.
- **One job for all appids.** The overlap guard is keyed on the job name, so a second click on any game while one refresh is in flight is refused with `ran: false`, the same "already running" shape the status triggers report. Per-appid guards would let several refreshes stack on the limiter at once; the control is a hand tool, not a queue.
- **Legs run in dependency order: schema, unlocks, rarity, enrichment, playtime.** `SteamPlayerUnlock` and the rarity rows are foreign-keyed to `SteamGameAchievement`, so the schema has to land first; `refreshUnlocksForGame` keeps its `achievementCount > 0` gate and the rarity leg is gated on the same meta read (its poller filters on that count; `refreshRarity` stamps the meta row unguarded, and a failed schema fetch may never have written one), so a schema-less game reports zeros rather than failing. Each service already isolates its own upstream failure into a `failed` count, so one refused leg does not stop the others.
- **Playtime is a library snapshot, not a per-app fetch.** Steam has no per-game playtime call; the number comes from `GetOwnedGames` over the whole library, and the service reports the game's before/after minutes around one `syncOwnedGames()` pass. The response and the UI copy say so, because a control labelled "this game" that quietly refreshes 160 rows should not surprise the reader of the status board. The snapshot runs outside the `steam-owned-games` job, so it can overlap the 15-minute poller; the writes are idempotent upserts in one transaction and the leg is caught, so the worst case is `playtime.failed: true` on one click.
- **Enrichment gets a per-appid entry through the existing `enrichApps([appid])`.** The poller's `refreshDue()` stays private: its job is selecting *which* appids are due, and the refresh already knows. One anonymous PICS logon per refresh is the cost of the logo leg; acceptable for a hand tool.
- **Own controller.** `SteamGameRefreshController` shares the `steam` prefix but not the class: `steam.controller.spec.ts` builds its testing module by hand in every test, so a new constructor dependency on `SteamController` would touch twenty-one provider lists for one route. The guard lint in `conventions.spec.ts` names the new file.
- **Owner-only, class-validated.** `@UseGuards(OwnerGuard)` per route like the status triggers; the appid arrives through `SteamAppidParamDto` (`@Type(() => Number)`, `@IsInt()`, `@IsPositive()`) rather than `ParseIntPipe`, so the same DTO can carry the route's future params. Curation is not consulted — the owner sees every game — but an appid outside the tracked library is a 404.
- **Web control is a mutation.** `useRefreshSteamGame` wraps `ownerRequest` in `useMutation` and invalidates exact owner-scoped keys — owned games, the single game row, library completion, completion candidates, the game's achievements, its unlock timeline, and the description and screenshot reads the store leg rewrites — rather than the `["steam", "game", appid]` prefix, which would also drop the public entries the loader primed. Each key comes from its hook's own `queryOptions` builder (the timeline and screenshot hooks gained one for this), so a key change there is a key change here. The result renders inline under the identity card's chip row as one clause per leg ("52 achievements in schema · 2 new unlocks · … · playtime up 15 min (library snapshot)"), with "unlock stats private on Steam" when that leg reports it; a refusal or a failed request is a toast, because the result line is for what changed. Visitors see the control locked with `OwnerAction`'s owner-only hint, the way the status page renders its triggers — the opposite call from the hide toggle beside it, whose own comment explains why a locked "hide" describes nothing. A second click while a run is in flight is disabled client-side and refused server-side.
